## 2026-09-21 자동 앱 갱신

사용자가 버전 번호를 확인하거나 '새 버전 적용'을 누르는 과정을 제거했다. 내부 데이터 프로토콜과 삭제 보호 규칙은 유지한다. 정상 데이터 동기화는 기존 Realtime/자동 재시도를 사용하며, 앱 파일 갱신은 별도로 자동 처리한다.

- 빌드 시 앱 내용으로 지문을 생성해 HTML·모듈 URL·Service Worker에 함께 넣는다. 같은 소스의 반복 빌드는 같은 결과를 내며 사람이 릴리스 이름을 바꿀 필요가 없다.
- 실행, 화면 복귀, 재연결과 1분 간격으로 새 앱을 확인한다. API가 호환성 갱신을 요구해도 사용자에게 버전 선택을 요구하지 않고 같은 자동 갱신 경로를 실행한다.
- 새 앱 전체를 캐시에 받은 뒤에만 전환한다. 화면이 사용되지 않는 짧은 틈에 자동으로 적용하되, 열린 입력창·텍스트 입력 포커스·한글 조합·드래그·기기 저장 실패/진행 중에는 기다린다. 평소처럼 저장하거나 입력창을 닫으면 자동 적용을 재개한다.

## 파일 구성과 저장 계약

- `src/app/sync/model.js`: 기존 화면 데이터를 항목·필드 묶음으로 변환, 변경 계산, 개인정보 범위 분리.
- `src/app/sync/repository.js`: 기기 저장·큐·확정본·초안·복구 사본을 관리하는 저장소.
- `src/app/sync/engine.js`: 전송 스케줄, 불변 요청, 누락 변경 수신, 충돌 해결, 계정 범위.
- `src/app/sync/controller.js`: 인증된 API, 비공개 실시간 채널, 첨부와 저장 상태 연결.
- `src/app/sync/status-ui.js`, `notes.js`, `comments.js`, `drafts.js`, `backup.js`, `lifecycle.js`: 사용자 화면과 복구·오프라인 동작.
- `src/app/sync/settlement-model.js`: 서버에서도 사용하는 순수 정산 계산. 저장 기준 금액은 원화 정수이며 내부 합산은 BigInt를 사용한다.
- `supabase/migrations/20260919143539_realtime_collaboration_v2.sql`: 항목, 영수증, 변경 이력, 첨부, 확정 정산, 서버 전용 명령 함수와 권한.
- `supabase/migrations/20260919143634_enable_sync_jobs.sql`: 운영 알림 재전송·기록 보관 작업.
- `supabase/migrations/20260919144121_fix_sync_service_auth_permissions.sql`: 운영 `service_role`에 없는 `auth.users` 직접 조회 제거. API의 `auth.getUser()` 검증과 기존 FK로 계정 존재를 확인하며 인증 테이블 접근 권한을 넓히지 않는다.
- `supabase/functions/triplog-sync/handler.ts`: 매 요청 `auth.getUser()` 검증 후 실행하는 API. 클라이언트의 actor·권한·정산 계산값은 신뢰하지 않는다.
- `supabase/ops/`: 알림 재전송·보관 작업 설치 및 운영 진단 SQL.

브라우저의 기기 확정본과 미전송 의도는 IndexedDB에 있다. 서버의 공유 확정본은 `triplog_entities`에 있다. 기존 `travel_state` JSON은 이관·복구 원본이며 새 쓰기 경로로 사용하지 않는다. 기존 테이블의 브라우저 직접 읽기·쓰기를 차단하므로 구버전 클라이언트와 새 스키마를 장기간 혼용하면 안 된다.

화면을 닫는 폼은 `await saveAndRender()`의 결과를 확인한다. `true`는 기기에 기록됐다는 뜻이며 서버 확정 상태와 구분한다. 요청이 진행되는 동안 생긴 추가 변경은 별도 큐 항목으로 남는다. 전송 준비 중 공동 메모가 합쳐졌다면 이전 본문으로 그 큐 전체를 완료 처리하지 않는다.

의미가 연결된 일정 시간, 위치 좌표, 이동 경비, 외화 금액·환율은 묶음으로 검사한다. 임의의 마지막 저장 시각으로 충돌 승자를 정하지 않는다. 로컬·서버의 출처를 확정할 수 없는 기존 차이는 자동 덮어쓰지 않고 이관 검토로 남긴다.

기기 자동 복구 사본은 여행당 최근 100개를 유지하며 최초 이관 원본은 이 제한에서 제외한다. 서버 변경 로그는 운영 보관 작업을 활성화하면 30일 보관한다. 중복 처리 영수증과 항목 삭제 표식은 자동 삭제하지 않는다. 이들의 저장량은 운영 진단에서 확인한다.

시험 계정 준비·정리용 임시 서버 경로는 추측 불가능한 일회성 비밀값과 고정 시험 식별자로 한정했다. 시험 데이터 정리 후 해당 코드를 제거하고 원래 API 번들과 동일한 SHA-256의 최종 version 4를 다시 배포했다. 일회성 세션·비밀값은 로컬에서도 삭제했다.

배포 후 Supabase Advisor의 RLS 정책 없음 안내 8개는 브라우저 직접 접근을 거부하고 검증된 서비스 API만 사용하는 테이블의 의도된 상태다. [RLS 안내](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy). 기존 프로젝트의 [유출 비밀번호 보호 미설정 경고](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)는 남아 있으며 이번 배포에서 요금제·인증 정책은 변경하지 않았다.

기존 Safari 화면에서는 작성 중인 항목의 추가·저장을 먼저 마친 뒤 TripLOG 탭과 홈 화면 앱을 닫고 다시 연다. 사이트 데이터는 지우지 않는다. 공유 여행을 연 뒤 `모두 저장됨`을 서버 확정 상태로 확인한다. `변경 내용 확인 필요`는 양쪽 후보가 보존된 상태이며 자동 덮어쓰기 대신 검토가 필요한 항목이다.

## 다음 운영 반영 시 절차

1. 별도 검증 프로젝트를 지정한다. 기존 SQL 연결은 조사 시 읽기 전용이었다. 실제 마이그레이션·함수·Storage·Cron·Pages 배포 권한과 프로젝트를 확인한다. 유료 프로젝트·요금제 변경은 자동 생성하지 않는다.
2. 운영 DB와 Storage의 백업을 만들고 별도 환경에서 복원 가능함을 확인한다. 브라우저 원본과 미전송 변경도 JSON으로 보관한다.
3. 기존 `supabase/triplog-collaboration.sql` 기반 스키마가 있는 검증 환경에 새 마이그레이션을 적용한다. 신규 환경이면 기존 기본 스키마를 먼저 설치한다.
4. `npm ci`, `npm test`, `npm run test:browser`, Edge 경계 테스트, `npm run build`를 실행한다. `_shared` 모델과 Yjs 번들은 수작업으로 편집하지 않는다.
5. `triplog-sync` 함수를 배포한다. 파일은 `index.ts`, `handler.ts`, `_shared/sync-model.js`, `_shared/settlement-model.js`다. SDK와 Yjs 버전은 import에 고정돼 있다.
6. `supabase/config.toml`의 `verify_jwt=false`는 무인증 허용이 아니다. 함수 내부의 `auth.getUser(bearer)`가 서비스 클라이언트 생성·명령 실행보다 먼저 검증한다. 실제 프로젝트의 인증 키·토큰으로 확인한다.
7. 실제 두 계정으로 로그인, 초대·권한, 비공개 Broadcast/Presence, 최대 크기 첨부 업로드·권한 변경 뒤 다운로드 차단을 시험한다.
8. `supabase/ops/enable-sync-jobs.sql`로 알림 재전송과 기록 보관을 활성화하고 실제 job 성공을 확인한다. 운영 진단은 `supabase/ops/diagnose-sync.sql`을 사용한다.
9. DB의 구버전 접근 차단과 새 Pages 클라이언트 배포를 한 전환 절차로 진행한다. 오래 열린 탭의 기존 로컬 자료를 지우지 않는다. 새 앱은 로컬 이관을 마친 후 서버에 연결한다.
10. 내부 시험 여행부터 운영 전환하고 실제 iPhone Safari와 홈 화면 앱에서 검증한다. 그 뒤 공개 범위를 늘린다.

배포 실패 시 예전 전체 JSON 쓰기를 다시 허용하지 않는다. API가 실패하면 기기 큐를 보존하고 서버 업데이트 필요·연결 재시도 상태로 남는다. 운영 DB 자체를 과거 백업으로 복구한 경우에는 클라이언트의 기존 커서·영수증과의 차이를 운영자가 대조해야 한다. 이는 단순 네트워크 재연결과 다른 복구 작업이다.

## 운영 전 별도 확인이 필요한 범위

- 실제 iPhone Safari의 앱 전환·화면 잠금·비행기 모드·홈 화면 실행은 아직 실기기로 검증하지 않았다. Edge의 모바일 폭 검증으로 대체했다고 표현하지 않는다.
- 실제 Supabase WebSocket 전파·Storage·알림 Cron 실행·인증·초대 토큰 수락은 위 운영 시험으로 확인했다. 실제 인증 메일 배달, 초대 링크를 서로 다른 실제 기기에서 열기, 일일 보관 작업의 첫 예정 실행은 별도 확인 항목이다.
- 10명 동시 편집·100개 연결, p95 지연, 큰 여행·장기 오프라인, 실제 DB·파일 복원 훈련은 출시 전 측정 항목이다. 99.9% 가용성이나 RPO/RTO 목표를 달성했다고 주장하지 않는다.
- 지속 저장 요청은 브라우저가 승인할 때만 적용된다. 사용자가 사이트 데이터를 지우거나 OS가 미전송 데이터를 없애는 상황까지 서버 백업이 보호할 수는 없다.
- 입력 초안 자동 보관은 일정·일반 지출 폼에 적용했다. 다른 폼은 기기 저장 완료를 확인한 뒤 닫도록 변경했으며, 모든 입력창의 저장 전 초안 복원을 동일하게 제공하는 것은 아니다.
- 메모의 상대 선택 위치는 Presence로 안내한다. 텍스트 편집기 위에 각 사용자의 색상 커서를 직접 겹쳐 그리는 UI는 포함하지 않았다.
- 정산 확정은 공유된 현재 여행의 원화 기준 장부를 검증한다. 실제 송금·결제, 은행 연동, 환율 공급자의 정산 보장은 포함하지 않는다.
- 진단 쿼리·로그·CI·복구 절차는 준비했지만, 외부 오류 추적·알림 채널과 유료 백업 계약은 활성화하지 않았다.
