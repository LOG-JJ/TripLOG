## 선택한 원안과 구현 범위

사용자가 [결제자 아래 분담 설정 목업](../../design/20261101-expense-item-split-refinement/allocation-component.png)을 선택하고 ‘이걸로 구현해줘’로 구현을 요청했다. 기존 지출 수정창의 결제자 아래에 한 개의 분담 영역을 추가했다. 목업의 좌우 패널은 같은 컴포넌트의 금액·비율 상태이며 실제 화면에는 현재 선택한 상태 하나만 표시한다. 기존 입력창과 `변경 내용 저장`을 재사용한다.

새 지출·빠른 입력의 크기를 바꾸지 않고 기존 지출을 수정할 때 표시한다. 음수 환불 기록에는 양수 분담 입력 UI를 노출하지 않는다. 외화의 분담은 기존 저장·정산 계약과 동일하게 원화 환산액을 기준으로 계산한다. 운영 데이터 변경이나 배포는 수행하지 않았다.

## 비교 과정과 수정

1. 초기 실제 캡처에서 접근성용 필드 설명이 보이는 상태로 입력값 위에 겹쳤다. 입력의 `aria-label`로 제공하고 필드 단위의 CSS 우선순위를 분리했다. 최종 [금액 비교](amount-comparison.png)에서 중복 설명과 단위 겹침이 사라진 것을 확인했다.
2. 320px의 비율 입력 열을 넓혀 소수 비율이 잘리지 않도록 했다. [소수 비율 캡처](percent-decimal-320-component.png)에서 33.33/33.33/33.34가 모두 보이고 합계 120,000원이 유지된다. 테스트에서도 실제 input의 가로 넘침을 검사한다.
3. 저장 실패 테스트의 일시적인 토스트가 캡처를 가리지 않도록 토스트 종료를 기다린 뒤 다시 캡처했다. 최종 두 비교 이미지는 같은 데이터와 모드의 대기 상태다. 실제 키보드 포커스 윤곽은 기능상 유지한다.

## 동작·저장 계약

- 입력 중에는 컴포넌트 초안만 변경한다. 닫기·취소는 원래 지출의 분담을 유지한다.
- 금액 모드에서는 원 단위 분담액의 합계가 결제 금액과 같아야 한다. 비율 모드에서는 0~100, 소수 둘째 자리까지 입력하고 전체 합계가 100%여야 한다. 음수·과도한 소수 정밀도와 안전한 정수 범위를 벗어난 금액은 저장할 수 없다.
- 비율을 원화로 바꿀 때 최대 나머지 방식으로 배분한다. 1,001원에 50/30/20%는 501/300/200원이고, 모드 전환만으로 기존의 원 단위 분담액을 다시 반올림하지 않는다.
- 기존 `settlement.itemSplits[current:<expenseId>]`의 `equal/custom`과 원화 shares를 재사용한다. 비율은 입력 방법이고 최종 정산은 원 단위 분담액이다. 기존 정산·백업·동기화 엔터티 구조를 확장하지 않았다. 기존 custom 분담은 다시 열 때 금액 모드로 표시한다.
- 한 지출과 그 분담을 같은 저장 스냅샷에 반영한다. 저장 false/예외 시 이전 항목·분담을 복원하고 작성값을 유지해 재시도할 수 있다. 다른 지출의 분담을 덮어쓰지 않는다.
- 편집 중 여행·계정·멤버 키·원본 금액·분담이 바뀌거나 대상이 삭제된 경우 저장을 중단한다. 기존 멤버에 없는 유효 분담액을 자동으로 버리지 않는다.
- 닫은 분담 입력은 DOM에서 비워 다른 항목이나 새 지출의 복구 초안에 섞이지 않도록 한다.
