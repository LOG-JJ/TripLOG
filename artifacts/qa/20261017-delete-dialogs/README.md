# 삭제 UI 검증 — 2026-10-17

삭제·초기화 확인창 16가지와 편집 중 제거 2가지를 취합하고, [T2I 목업 5장](../../design/20261017-delete-dialogs/README.md)을 기준으로 구현했습니다. 이 문서는 배포 전 로컬 구현·빌드·검증 결과를 기록한 문서이며, 운영 배포 상태는 포함하지 않습니다.

## 크기와 문구

| 확인 항목 | 기존 | 개선 |
| --- | --- | --- |
| 모바일 390×844의 일반 일정 삭제창 | 350×675.19px | 342×160.19px |
| PC 1440×1000의 일반 일정 삭제창 | 420×800px | 342×160.19px |
| 제목 | 확인해 주세요 / 22px | 일정을 삭제할까요? / 18px |
| 내용 | 삭제 대상과 질문을 한 문장으로 표시 | 대상 이름, 필요한 영향 안내만 표시 / 14px |
| 실행 버튼 | 확인 | 삭제·보관·초기화·내보내기·나가기 |
| 터치 영역 | 화면 아래 멀리 배치 | 본문 바로 아래, 버튼 높이 44px 이상 |

일반 일정 삭제창의 높이는 같은 모바일 fixture에서 **76.28%** 감소했습니다. 표준 문구 16가지의 실제 높이는 160.19~208.19px이며, 긴 이름·댓글은 내용 영역에서 스크롤해 전체를 읽을 수 있습니다. 작은 화면에서 과도한 빈 공간, 가로 넘침, 버튼 잘림은 발견하지 못했습니다.

## 목업 대조

| 비교 지점 | 구현과 확인 결과 |
| --- | --- |
| 구성 | 짧은 질문 → 대상 → 필요한 영향 → 나란한 두 버튼. 대상·설명이 없으면 해당 줄을 생략합니다. |
| 크기 | 최대 폭 342px, 내용에 맞는 높이, 모바일·PC 모두 중앙 배치. |
| 글자 | 제목 18px, 대상·설명·버튼 14px. 실제 computed style을 확인했습니다. |
| 색상 | 흰 바탕, 얇은 어두운 테두리, 작은 그림자, 흰 취소 버튼과 붉은 실행 버튼. 복원 등 비삭제 확인은 기존 노란색을 사용합니다. |
| 문구 | [제작 브리프](../../design/20261017-delete-dialogs/brief.json)의 16가지 질문·영향·실행 버튼 문구를 모두 대조했습니다. 이름·금액·날짜는 실제 선택한 대상에서 가져옵니다. |
| 입력 중 제거 | `첨부 제거`, `구간 삭제`와 저장 시 반영된다는 짧은 안내를 표시합니다. 저장 전에는 원본 데이터가 유지됩니다. |
| 접근성 | 취소를 처음 포커스하고 키보드·Escape·바깥 클릭·포커스 복원을 확인했습니다. 포커스 링과 긴 텍스트의 스크롤 접근은 목업에 추가한 접근성 표현입니다. |
| 배경 화면 | 생성된 목업의 배경은 크기를 설명하기 위한 예시입니다. 실제 앱의 내비게이션과 일정·예약 편집기 구조를 유지했습니다. |

5개 목업 보드와 최신 브라우저 캡처를 직접 대조했습니다. 확인창의 구성·문구·타이포그래피·간격·색상에서 해결하지 않은 차이는 없습니다. 기존 편집기 구조, 포커스 링, 실제 데이터 표시는 위에 명시한 의도된 차이입니다.

## 기능 검증

검증 흐름은 **해당 화면 진입 → 삭제 버튼 → 작은 확인창 → 취소 시 원본 유지 / 실행 시 해당 대상만 저장 후 제거 → 재접속·새로고침 확인**입니다.

- 16가지 확인창 × 320·390·599·600·768·1440px = **96개 상태·화면 크기 조합**을 검사했습니다.
- 일반/지출 연결 일정, 지출, 예약, 준비물/초기화, 정산 멤버, 저장 기록, 초안, 지도 키, 기록 초기화, 댓글, 멤버 내보내기와 여행 나가기를 실제 UI 경로에서 확인했습니다. 여행 목록 삭제·공유 여행 보관·복구는 기존 여행 선택 회귀 테스트에서 검증했습니다.
- 취소·기본 취소 버튼에서 Enter·Escape·바깥 클릭, 중첩 편집기 유지, 이전 컨트롤로 포커스 복원, 중복 확인창 차단을 검사했습니다.
- HTML처럼 보이는 긴 대상 이름이 안전한 텍스트로 표시되는지, 320px에서 200% 글자로도 내용과 버튼에 접근할 수 있는지 확인했습니다.
- 연결된 일정은 유지되는 지출 삭제, 연결 지출까지 함께 지우는 일정 삭제, 예약 원본 보존을 검사했습니다.
- 저장 실패 시 지출과 입력창 유지, 정상 저장 재시도, 삭제와 준비물 초기화의 새로고침 후 유지를 확인했습니다.
- 기록 초기화의 문구가 실제 동작인 ‘기존 여행 보존·저장 스냅샷 삭제·새 여행 생성’과 일치하는지 확인했습니다.
- 다중 기기 일정 삭제·오프라인 재접속·삭제 복구, 기존 예약/지출/정산/지도/내보내기/로그인/캐시/드래그 기능까지 전체 브라우저 회귀 테스트를 통과했습니다.

| 검사 | 결과 |
| --- | --- |
| 페이지 URL·제목 및 의미 있는 본문 | 통과 |
| 빈 화면·오류 화면·예기치 않은 콘솔 오류 | 없음 |
| 목업과 실제 캡처 대조 | 통과 |
| 취소·실행·저장·새로고침 | 통과 |
| `npm test` | 통과 |

| `npm run artifacts:check` · `git diff --check` | 통과 |

기계가 읽을 수 있는 크기·동작·빌드 검증 값은 [verification.json](verification.json)에 있습니다. 빌드 지문은 `9808e28a7994da3e9ea2`이며, HTML과 서비스 워커가 일치합니다. 새 확인창 모듈은 빌드·캐시에 포함되고 목업·QA 자료는 포함되지 않습니다.

검증 환경은 Windows의 격리된 Playwright/Edge입니다. Browser 플러그인과 browser 스킬이 세션에 없어 기존 프로젝트의 Playwright 도구를 사용했습니다. 외부 요청과 서비스 워커를 차단한 fixture의 예상 메시지는 제외하고, 앱 런타임 오류와 예기치 않은 콘솔 오류는 없었습니다. 실제 사용자의 여행 데이터는 사용하지 않았습니다. 물리적인 iOS Safari·Android 기기 검증과 실제 서비스에서의 멤버 삭제·나가기 실행은 포함하지 않습니다.
